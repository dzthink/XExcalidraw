## 结论

优先优化共享 Web 编辑器的局部更新与原生主线程保存链路。两端都使用 WKWebView，输入卡顿不能只看 SwiftUI。当前 1000 节点导图在 macOS WebKit 合成测试中，编辑事务加 React 提交 P95 为 **21ms**，相邻 rAF 回调间隔 P95 为 **103–104ms**，编辑器挂载至两个 rAF 为 **636–644ms**。三次运行结果接近。已有代码足以解释这些随规模增长的开销。

大纲目前比导图编辑快，但 1000 节点会同时挂载 1000 个 ProseMirror 编辑器；长期内存和大规模滚动仍需要优化。原生端也有独立瓶颈：iOS 同步打开文件、两端同步解析桥接 JSON 和持久化全量索引、保存引起目录树重建。

这些数据是本机合成基准，不是 iPhone 真机、应用完整启动或实际屏幕帧率的测量。后续验收必须覆盖真机、中文输入法、图片和 iCloud。

## 测量方式与结果

- 本机 arm64，Node `v26.7.0`，Xcode `26.1.1`；原生基准 `swiftc -O`。
- 数据基准直接编译当前 `document.ts`；原生基准编译当前文件条目、索引存储和文件树实现。
- WebKit 基准在独立 WKWebView 中加载生产模式打包的 `MindMapEditor`，1280×900，非持久化网页数据，全部节点展开，无图片。通过 ProseMirror 事务模拟插字，`flushSync` 包含 React 提交；不是系统键盘或 IME 测量。

## 1. P0：导图每次输入都访问全图并重新计算连线

证据：[`MindMapEditor.tsx:305`](../../web/canvas-host/src/MindMapEditor.tsx#L305) 的无依赖 `useLayoutEffect` 在每次 React 提交后构造整棵拓扑、逐节点 `findEle`、比较 HTML、更新 CSS class。[`RichEditor.tsx:46`](../../web/canvas-host/src/mindmap/RichEditor.tsx#L46) 每次事务，包括选区变化，都调用 `onActive` 和 `onResize`；[`MindMapEditor.tsx:109`](../../web/canvas-host/src/MindMapEditor.tsx#L109) 总是设置新的 active 对象，触发父层更新。`resize()` 通过 rAF 调用全图 `linkDiv()`。

当前安装的 `mind-elixir/dist/MindElixir.js:339` 中，`findEle` 是对整个编辑器的 `querySelector`，不是节点字典查找；`:1331` 的 `linkDiv` 清空连线，再读取节点尺寸并重新生成 SVG。遍历中反复查询 DOM、几何读取与 SVG 写入交错，是重要的规模成本。rAF 只合并调度，不能让一次 100ms 工作变成 5ms。

优化：

- 保存 `id → HTMLElement`、`id → node`、`id → parent` 索引；结构变化后维护或重建，内容变化直接定位节点。
- 分开 content / structure / selection / viewport revision。选区和保存状态更新不能引发全图同步。
- 文本变化只更新对应节点；节点尺寸没变时不重算连线。对活跃节点观察实际尺寸变化，而不是每个选区事务都调用 `onResize`。
- 连线更新缩小到受影响分支，先批量读取几何再写 SVG；避免读取和写入交错。保留全图计算用于确实影响全图的布局切换。
- 保留现有节点 HTML 缓存和 transform 平移缩放路径；不把平移改成全图刷新。

验收：1000 节点编辑事务 P95 <5ms；移动光标不触发全图 `linkDiv`；文本变化但尺寸不变时不重新生成 SVG。重新录制 WebKit Timelines 确认布局与 JS 开销下降。

## 2. P0：原生保存与索引更新仍阻塞主线程

证据：macOS [`handleSave:949`](../../apps/macos/Sources/ExcalidrawMac/App/ExcalidrawMacApp.swift#L949)、iOS [`handleSave:2172`](../../apps/ios/Sources/ExcalidrawIOS/App/ExcalidrawIOSApp.swift#L2172) 在脚本消息回调中解析内层 scene 并遍历校验。SDK 中 `WKScriptMessageHandler` 标注 `WK_SWIFT_UI_ACTOR`。`deliver()` 也在 UI 路径中编码整份文档并转义成 JS 字符串。

正文写入虽已在 `saveQueue`，但 [`DocumentManager.swift:206`](../../apps/shared/Sources/ExcalidrawShared/DocumentManager/DocumentManager.swift#L206) 返回主线程后删除草稿、读取文件元数据、更新索引；[`FolderSourceStore.swift:506`](../../apps/shared/Sources/ExcalidrawShared/Stores/FolderSourceStore.swift#L506) 调用同步 `persistIndexEntries()`，再次编码和原子写入整份索引。[`DocumentManager.swift:374`](../../apps/shared/Sources/ExcalidrawShared/DocumentManager/DocumentManager.swift#L374) 还在主线程 `saveQueue.sync`；若后续保存已排队，UI 可能等待另一次写入。重命名的 `saveQueue.sync` 同样存在等待风险。

优化：把消息解析、校验、元数据读取、草稿清理和索引持久化放到受控工作队列。UI 线程只接受结果和更新少量状态。索引内存更新立即完成，磁盘持久化合并调度；保存确认以文档可靠落盘为准，不让派生索引决定文档保存时延。重命名映射在保存队列内解析完毕随结果返回，去掉主线程同步等待。

须同时明确线程所有权：目前 `createBlankDocument` 的后台路径会调用 `store.upsertEntry` 更新 `@Published` 状态，不能只把更多代码搬到后台而继续共享可变状态。采用主线程拥有 UI 状态、串行 worker 拥有磁盘状态及不可变快照的方式。

验收：保存期间原生主线程不执行文档 JSON 解析、索引编码、写盘或队列同步等待；输入时触发自动保存不能产生可见停顿。

## 3. P0：iOS 打开与启动恢复仍同步读文件

证据：iOS [`restoreLastOpenedFile:193`](../../apps/ios/Sources/ExcalidrawIOS/App/ExcalidrawIOSApp.swift#L193)、两个列表的 [`openEntry:568`](../../apps/ios/Sources/ExcalidrawIOS/App/ExcalidrawIOSApp.swift#L568)、[`openEntry:1328`](../../apps/ios/Sources/ExcalidrawIOS/App/ExcalidrawIOSApp.swift#L1328)、[`loadInitialScene:2285`](../../apps/ios/Sources/ExcalidrawIOS/App/ExcalidrawIOSApp.swift#L2285) 使用同步 `DocumentManager.open()`，其中是 `Data(contentsOf:)`、JSON 解析与索引写入。页面恢复与 Web 导航完成还有重复加载最近文档的可能，需统一启动状态机。

macOS [`open:1035`](../../apps/macos/Sources/ExcalidrawMac/App/ExcalidrawMacApp.swift#L1035) 已有异步 read、generation 防止旧结果覆盖、loading/error 状态，是可沿用的基础。

优化：iOS 统一使用异步打开流程，先处理当前文档保存屏障，再读取目标文件，接受最新 generation 的结果后激活。轻量反馈与导航立即响应；iCloud 下载单独显示进度，允许取消/换文件，过期结果不覆盖新选择。消除多处重复恢复逻辑。

验收：本地打开按现有规格 <300ms；iCloud 等待期间导航、取消和滚动始终响应。需要同时测“点击到反馈”和“点击到可编辑”，不能只以读取回调完成为终点。

## 4. P0：每次编辑全量复制文档，撤销历史保留全量快照

证据：[`document.ts:111`](../../web/canvas-host/src/mindmap/document.ts#L111) 每次 change 都 `JSON.parse(JSON.stringify(document))`，再对 before / after 全量 stringify 比较；即使属于同一个输入分组，也执行完整复制和比较。历史最多 200 份完整文档，undo / redo 再复制整份。

5000 节点连续输入的数据层 P95 已达 17.23ms；合成文档的 200 份 UTF-8 序列化副本合计约 **482MiB**。这是描述全量快照规模的量纲估算，**不是已测得的 JS 堆内存**；真实对象、共享字符串、GC 与节点复杂度会改变占用。

优化：用节点内容的 ProseMirror steps / inverse steps 和树结构命令的逆操作保存统一历史，或采用持久化树与结构共享。至少先做到同一分组只保存一次起始状态、显式报告实际变更，避免全量字符串比较。限制历史字节预算，视图位置信息与内容历史分离。保留现有跨大纲/导图撤销及光标恢复语义。

验收：编辑一个节点的工作量随该节点内容增长，不随全篇节点数增长；200 次分组操作后的内存增长受预算控制；撤销不能丢失富文本、选区和输入法状态。

## 5. P1：大纲挂载所有展开节点的完整编辑器

证据：[`MindMapOutline.tsx:34`](../../web/canvas-host/src/MindMapOutline.tsx#L34) 递归为所有展开节点渲染 RichEditor，每个都创建 EditorState、EditorView、表格插件及 DOM 观察器。父层每次 active 更新也会重新生成整份展开树。

优化：非活跃节点使用缓存的静态富文本，仅正在编辑的节点挂载 ProseMirror。必要时对扁平化可见行做窗口化，使用稳定节点 ID、行高缓存和 overscan。活跃行、IME composing 节点、选区及拖拽目标必须保持挂载；不能直接把正在输入的 contenteditable 移出 DOM。先稳定行级数据和回调，单加 `React.memo` 无法绕过所有不稳定 props。

验收：1000 / 5000 节点长文档的编辑器实例数量有界；滚动、跨节点键盘导航、撤销、变高表格和图片加载都保持正确。

## 6. P1：保存和最近打开时间更新会触发目录扫描与树重建

证据：macOS [`indexedEntries onChange:244`](../../apps/macos/Sources/ExcalidrawMac/App/ExcalidrawMacApp.swift#L244) 调用 `rebuildFileTrees()`，在 UI 路径遍历所有源目录。iOS [`onChange:506`](../../apps/ios/Sources/ExcalidrawIOS/App/ExcalidrawIOSApp.swift#L506) 同样触发 `rescanFolders()`。`updateEntryAfterSave` / `updateLastOpenedAt` 都改变 entries。`FileTreeNode` 每次构建使用随机 UUID，完整替换节点会损失身份与展开状态，并增加 SwiftUI 更新。

`FolderSourceStore` 虽在后台扫描且已有 400ms 防抖，但本地目录 watcher 和 iCloud metadata 更新各自排队扫描；防抖不会取消已入队的扫描。正文原子写入也可能触发目录事件，产生“保存 → 索引更新 → 重建树 → 再扫描”的额外工作；实际触发频率需用 signpost 核实。

优化：结构变化和元数据变化分开发布；只有新增/删除/移动/目录结构变化需要树结构更新。索引扫描顺便收集空目录，UI 不再重复遍历磁盘。按源/相对路径保持节点身份与展开状态，只更新变化条目。扫描合并同源请求、带 generation 丢弃过期结果，发布前比较实际差异。对自身写入事件做可验证的去重，同时保留外部修改检测。

验收：编辑内容、更新最近打开时间不触发目录遍历；一次实际目录变更只有必要的一次更新；侧栏展开状态保持。

## 7. P1：桥接消息过密与保存放大

证据：[`App.tsx:419`](../../web/canvas-host/src/App.tsx#L419) 每次 Excalidraw onChange 都发送 didChange；原生两端不比较旧状态就写 `@Published`。CanvasSession 转发 manager / viewModel 的所有 objectWillChange，容易扩大视图重算范围。当前保存 scene 是 JSON 字符串，再嵌入外层 JSON；原生再次解码。每次保存草稿与正文各自编码、原子写入。

优化：dirty 只在状态转变时通知；按内容、视图位置、临时选区区分保存需求，视图位置低频保存，保持产品现有恢复语义。去掉重复编码链，原生在 worker 校验 JSON 后可复用数据；协议升级再考虑文档读取走 URL scheme、桥接仅传 ID / revision。正文落盘确认需绑定 docId / generation / revision，避免旧保存确认把新编辑状态清为已保存。

先保留草稿和原子落盘保障，合并可合并的同文档后台保存；不要通过延长防抖或删除草稿来掩盖卡顿。切换、退出和后台保存屏障必须保留。当前 `siyeFlush` 主要覆盖思维导图，Excalidraw 的防抖保存取消/切换语义应在改链路前补齐验证。

验收：dirty 状态稳定后不持续跨桥发送；大量绘图变化不引发原生页面反复更新；自动保存和强制保存都确认对应版本已可靠写入。

## 8. P1：图片跨桥往返、同步资源读取与解码内存

证据：iOS [`documentPicker:2029`](../../apps/ios/Sources/ExcalidrawIOS/App/ExcalidrawIOSApp.swift#L2029) 同步读图片并 base64 发送到 Web；[`NodeToolbar.tsx:78`](../../web/canvas-host/src/mindmap/NodeToolbar.tsx#L78) 解码成 File，随后 [`MindMapEditor.tsx:161`](../../web/canvas-host/src/MindMapEditor.tsx#L161) 再读 base64 发回原生保存。两端 attachment handler 也在派发后台写入前解码 base64。Scheme handler 在 `start` 中同步 `Data(contentsOf:)`，`stop` 为空；SDK 将 `WKURLSchemeHandler` 标注为 UI actor。图片 DOM 没有懒加载或缩略图层。

优化：原生选图直接在后台保存附件，只把相对路径和尺寸回传 Web，保留光标 bookmark 与失败恢复。资源加载移至 IO 队列，UI actor 安全回调，显式处理取消，禁止已 stop 的 task 再回调。限制并发请求，设置有界缓存；显示使用按像素尺寸生成的预览，导出仍用原图。10MB 文件上限不能约束解码内存，例如 6000×4000 的 RGBA 像素约 96MB（十进制）。

验收：插入较大图片时页面和键盘响应；滚动加载图片不阻塞主线程；100 张图片的峰值内存受控，离开文档后可回落。该场景本次未实测。

## 9. P1：WebView 生命周期有强引用环风险

两端 ViewModel 持有 webView，同时把 self 注册为 script handler，未发现 remove handler 或显式 teardown。链路是 `ViewModel → WKWebView → WKUserContentController → script handler → ViewModel`。WebKit 源码以 `RetainPtr<id>` 保存 handler，支持这一风险判断：[WKUserContentController.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKUserContentController.mm)。macOS 多窗口反复开关时尤其值得检查。

优化：使用弱引用 handler 代理；在真实会话关闭时移除 handler、停止加载、取消定时器与待处理任务。iOS 返回文件列表仍可保留当前 WebView 以便快速恢复，不要在每次导航时销毁重建。仅把 cleanup 放在 ViewModel deinit 无法自行解除已经阻止 deinit 的引用环。

验收：反复新建/关闭窗口后 ViewModel 与 WebView 释放；内存、Web 内容进程和后台唤醒不持续累积。此项是引用关系分析，还没有跑 Allocations / Leaks 验证。

## 10. P2：冷启动负载、空闲轮询与键盘消息

- `App.tsx` 静态导入 Excalidraw 与思维导图，初次打开任何一种文档都会加载两套模块。当前代码重新构建的入口 JS 为 **1,681,483B**，完整 dist 为 **8,413,738B**；入口数字不等于所有动态 chunk 都会首次加载。考虑编辑器按文档类型 lazy import，明确 webReady 与 editorReady，预热常用类型，避免从冷启动负担转成每次切换等待。
- [`bridge.ts:76`](../../web/canvas-host/src/bridge.ts#L76) 的 cursor tracking 在鼠标移动和每 50ms 查询样式，且也初始化在 iOS；没有 cleanup。生产单次挂载已有空闲唤醒，开发 StrictMode effect 重放还可能重复注册。改成初始化幂等、支持释放，仅桌面启用，按鼠标事件 rAF 合并、页面隐藏时停止；用事件或受限观察器替代长期轮询。
- iOS accessory 每次 layoutSubviews 都发送 JS 键盘坐标。已有 Web 端 rAF 合并，但 native → Web 消息仍可先比较位置、可见状态再发送；键盘动画期间记录消息次数，避免重复尺寸通知引发布局。现有 UIKit accessory 与 visualViewport 路径保留。
- 原生索引在 FolderSourceStore 初始化时同步加载，启动对大量历史索引可先展示轻量界面再后台恢复。
- 样式的模糊/阴影目前不应排在前面：先解决已测到的 JS、DOM 查询、连线与主线程 IO，GPU 成本通过 trace 再判断。

## 流畅度验收建议

现有规格已经要求冷启动可点击界面 <1s、本地文档可编辑 <300ms，见 [native spec](../excalidraw_native_spec_v1.md#62-性能硬性指标)。建议补充明确的文档规模和设备范围，避免对无限大文件作无条件承诺。

| 场景 | 建议目标与测量 |
| --- | --- |
| 常用 100–1000 节点、复杂 5000 节点 | 分别记录输入处理 P50/P95/P99、打开到可编辑耗时、内存峰值；5000 节点要求活跃工作量有界 |
| 拖拽/缩放/滚动 | 在实际设备刷新率下稳定出帧，UI/JS 关键路径尽量 <5ms；不只看平均 FPS |
| 点按/菜单/折叠 | 反馈 <100ms，持续交互不发生长任务堆积 |
| 自动保存同时输入 | 原生主线程无磁盘等待、全文解析或全量索引写入；Web 无不必要全图布局 |
| 中文 IME、表格、图片 | 真机验证 composition、光标/选区、键盘开合与图片异步加载 |
| iCloud 未下载、快速连点切文件、前后台切换 | UI 及时反馈，过期结果丢弃，退出/切换保存不丢内容 |
| 长期运行、多窗口 | 200 次分组撤销、连续编辑 30 分钟、反复开关 20 个窗口，内存无持续增长 |
| 文件库 | 100/1000/10000 条目；保存正文不重建目录结构，不丢侧栏展开状态 |

上述 5ms / 100ms 与帧期限参照 [Apple Improving app responsiveness](https://developer.apple.com/documentation/xcode/improving-app-responsiveness)，是工程目标而非本次已经达成的结果。Apple 建议用真机检查 hitches；本地 Node 或模拟器数字无法证明 iPhone 流畅。

原生用 Release 构建、Time Profiler、Hangs/Hitches、Allocations/Leaks，以及 Xcode 26 SwiftUI instrument 排查更新原因，参照 [WWDC25 SwiftUI performance](https://developer.apple.com/videos/play/wwdc2025/306/)。Web 内容进程单独通过 [WebKit Timelines](https://webkit.org/web-inspector/timelines-tab/) 测 JS、布局和帧，不能只 profile 原生宿主。为 OpenDocument、DeliverScene、HandleSave、PersistIndex、ScanFolder、BuildTree 加 signpost；Web 对 transaction、render、linkDiv、serialize 加 performance marks，并用 requestId / revision 对齐两个进程。
